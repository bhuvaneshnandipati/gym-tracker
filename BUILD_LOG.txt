AUTO-SAVE BEHAVIOUR (debug reference)
------------------------------------------------------------------------------
  Trigger      any draft change -> useMemo(buildPayload) -> JSON fingerprint
  Debounce     800 ms; timer cleared and rescheduled on each change
  Dedup        write skipped when fingerprint === last persisted fingerprint.
               The workout id is EXCLUDED from the fingerprint, so the
               insert -> update transition does not cause a redundant write.
  Concurrency  one write in flight; edits during a write are coalesced into a
               single follow-up write (runningRef / queuedRef)
  First save   INSERT returns an id -> stored in workoutIdRef -> URL replaced
               with /workout/:id -> all later saves are UPDATEs.
               `initialised` guard prevents the fetched row from clobbering the
               live draft; `useWorkout(id, !hydrated)` disables that refetch.
  Failure      status 'error' + Retry; NOT auto-retried (prevents write loops).
               Next edit or reconnect reschedules.
  Offline      detected before dispatch; status 'offline (will sync)'; flushed
               on reconnect. Existing paused-mutation resume left intact.
  Unload       flush on visibilitychange->hidden and pagehide (best effort);
               beforeunload warns while still dirty.
  Statuses     idle | Saving… | Saved | Offline (will sync) | Save failed

  KNOWN BEHAVIOUR: api/workouts.saveWorkout replaces child rows on update
  (delete + re-insert). Unchanged by design. Per-field diffing at the row level
  would require an API/schema rewrite; de-duplication is therefore done at the
  payload level, which is what prevents redundant writes.

SUGGESTION RULES (F4) — weight_reps only, >= 2 prior sessions
------------------------------------------------------------------------------
  increment = 5 lbs (2.5 kg), applied to the top set of the last session
    reps >= 12 -> weight + increment, 8-10 reps
    reps >=  8 -> weight + increment, 6-8 reps
    reps <   8 -> same weight, reps+1 to reps+2
  Worked example: last 240 x 8 -> "245 lbs x 6-8 reps" (matches spec).
  Display only; never written into any input.

  - Two contexts (actions vs live state) so set rows / the editor do not
    re-render on the 250 ms display tick.
  - Audio cues pre-scheduled on the Web Audio clock (survives JS throttling);
    deferred until the AudioContext is unlocked by a gesture.
  - No new dependencies. No database migration (duration_seconds existed).
